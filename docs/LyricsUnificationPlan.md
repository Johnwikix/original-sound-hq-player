# 歌词存储合并与迁移方案

日期：2026-09-29。状态：已按确认方案实现，测试证据与支持边界见第 12 节；未操作用户实际数据库。

## 1. 结论与范围

将目前按格式划分的 `Lyrics / TranslatedLyrics / Krc / TKrc` 合并为一份原文和一份翻译。原文保留其格式，翻译统一保存为逐行 LRC；原文格式不再决定数据库列、缓存字段和业务调用链。

按本次讨论补充的边界：

- 原文与翻译分别保存为独立文本；导出时各一份文件。翻译只需行级时间，不保留逐字动画数据。
- 不自动识别文本语言，也不在领域模型或数据库新增 Language 字段。
- 不识别同一个 LRC 中的双轨组合，不根据同时间戳、行次序、文字语言猜测翻译或发音。
- 将来支持发音时，再增加一份独立文本及对应文件。本轮不实现发音显示，也不引入任意轨道注册系统。
- TTML 是一种输入格式。其明确标注的翻译可在导入边界拆出，进入上述两份内容的模型；不把 TTML 转成普通 LRC 后再作为唯一存档。
- 此次覆盖统一存储、解析入口、文件优先级和 TTML 接入的设计；不扩展为歌词编辑器或完整 TTML 排版引擎。

对应 [issue #27](https://github.com/Johnwikix/original-sound-hq-player/issues/27)：文件优先级自定义、TTML 支持纳入本轮；同文件双轨 LRC 明确排除；发音作为以后增加独立内容的扩展点。

## 3. 统一模型

业务模型建议保持简单：

```csharp
// 提案代码，具体持久化类型与领域类型分离。
public sealed record LyricsText(
    string Content,
    LyricsFormat Format);

public sealed record LyricsDocument(
    LyricsText Original,
    string? TranslationLrc);

// 以后确实实现行级发音时，增加 string? PronunciationLrc。
```

`LyricsFormat` 区分 Unknown、Lrc、EnhancedLrc、Krc、Qrc、Ttml。普通／增强 LRC 可以共享 `.lrc` 文件后缀，但解析器仍需区分它们。若保留既有特殊语法兼容分支，应在解析器内部明确命名，不把它继续伪装成标准 KRC。

约束：

1. `Original` 记录原文格式，`TranslationLrc` 固定为普通逐行 LRC，不再重复记录翻译格式。QRC/KRC/TTML 原文搭配 LRC 翻译是标准保存方式，翻译不需要跟随原文逐字。
2. 原文格式由来源提示加内容探测确定；后缀只用于发现候选。保存时校验格式与文本，旧原文探测失败则保留 Unknown 和原始内容。翻译输入可以来自其他格式，但必须在导入边界转成逐行 LRC 后进入活动文档。
3. 两份内容是一组保存快照。刷新失败、取消或翻译暂缺，不得用一组空字符串覆盖已有有效内容。
4. 解析结果是派生数据，不把 WinUI 的 `ObservableObject` 或可变 `LyricLine` 直接序列化进数据库。
5. 原文与翻译的关联属于这组内容，不默认把未选中旧版本的翻译拼到新原文上。
6. 原始歌词时间和用户 `LyricsOffsetMs` 分离；动画提前量只影响显示投影。
7. `Language` 不参与播放、时间对齐或单份翻译保存，因此不进入模型。TTML 自带的 `xml:lang` 可以由导入器读取以选择已有翻译，它是来源明确提供的元数据，不是对文本进行语言识别；保存后不再按系统语言过滤翻译。

建议用新的 `MusicLyricsV2` 表隔离新旧结构，业务层仍通过统一仓储访问：

| 字段 | 用途 |
| --- | --- |
| `MusicId` | 主键；仅库内曲目使用 |
| `Lyrics`、`LyricsFormat` | 原文及格式 |
| `TranslatedLyrics` | 可选逐行 LRC 翻译，格式由模型约定固定 |
| `SourceKind`、`SourceKey` | 当前这组内容的来源；迁移数据允许 LegacyUnknown |
| `Revision` | 乐观并发版本，阻止迟到下载覆盖用户编辑 |
| `SchemaVersion`、`MigratedFromHash` | 结构版本与旧数据迁移指纹 |

`SourceKey` 只记录歌曲资源或提供方标识，不包含 WebDAV 密码或带凭据的 URL。无需提前为每个格式建立子表。以后增加行级发音，只增加可空的 LRC 内容字段，旧记录默认无发音；不预先增加语言识别或逐字发音模型。

一首歌在新结构中只有一组活动内容。旧版两组均有数据时，未选中的一组保留在旧表／备份中用于恢复，不再作为另一套日常播放缓存。

## 4. 职责与依赖

```text
播放 / 手动重新获取 / 详情编辑 / 扫描 / 一次性播放
                         ↓
                歌词加载与保存用例
                         ↓
          来源选择 → 读取 / 下载 → 输入解码
                         ↓
           格式识别 → 显式解析 → 翻译关联
                         ↓
             LyricsDocument + 只读解析快照
                    ↙              ↘
           统一仓储 / JSON缓存     UI显示投影
                                     ↓
                            主界面 / 桌面歌词
```

建议围绕以下职责拆分，不要求每项都建立一个只有转发方法的类：

| 职责 | 所有权与边界 |
| --- | --- |
| `LyricsLoader` | 当前加载请求、取消、代次、UI 发布；不解析语法、不递增播放次数 |
| `LyricsResolver` | 来源选择、回退、自动／手动刷新策略；接收不可变曲目与偏好快照 |
| `LyricsParser` | 纯文本解析、格式识别和翻译关联；无数据库、网络、App.Services 或 ViewModel 依赖 |
| `LyricsRepository` | 库内统一读写、迁移、版本比较；一次性缓存复用同一文档 DTO 和迁移算法 |
| `LyricsExporter` | 两份独立文件和标签导出；不能仅通过修改后缀转换格式 |
| 显示适配层 | 将只读解析结果转换为现有渲染输入；持有 UI 对象与显示设置 |

在线服务按“提供方＋请求能力”命名，例如 QQ 逐字、网易逐行、QQ 逐行；返回同一个 `LyricsDocument`，不再用 GetKrc/GetLrc 名称决定存储位置。封面方法可以先留在现有服务中，避免扩大本轮范围。

所有显式“重新获取”入口共用同一个用例、取消契约和保存规则。旧 `ToolUtils.GetLyricsFromNet/GetKrcFromNet` 的便利方法应删除或转为短期适配，不再绕过真实 HTTP 取消。

## 5. 来源、文件优先级与翻译文件

### 5.1 文件顺序

增加持久化偏好 `LocalLyricsFormatOrder`，例如用户可选择：

```text
ttml → lrc → krc → qrc
```

顺序仅决定同目录、同歌曲名的主歌词候选。它不决定翻译语言、不把格式优先级套到所有在线提供方上。

存量用户默认保留 `.krc → .qrc → .lrc`，将 `.ttml` 追加在后，避免升级后无声切换已有歌词；提供 TTML 优先的预设。新增偏好校验去重、忽略未知项并补齐新增格式，顺序由 ViewModel/偏好状态持有，视图只转发操作。

按顺序尝试“存在、读取成功、解码成功、解析出有效原文”的第一个候选。高优先级文件为空、损坏或格式不支持时继续回退；取消必须终止本轮，不能当作文件损坏继续搜索。读取加密／压缩 KRC/QRC 应先按字节头解码，不能统一 `ReadAllText` 后靠正则猜测。

### 5.2 两份独立文件

保留当前 `_Translated` 命名约定：

```text
Song.ttml                 原文
Song_Translated.lrc       翻译，固定逐行 LRC

// 未来单独实现：
Song_Pronunciation.lrc    发音
```

配套翻译优先查 `_Translated.lrc`。为兼容既有文件，未找到有效 LRC 时再查主文件同后缀及其余已支持后缀，解析后转换成逐行 LRC；同一后缀只尝试一次，源文件不改写。新导出固定生成 `_Translated.lrc`，翻译文件不再随主歌词优先级设置改变标准格式。永远不把 `_Translated` 文件作为主歌词候选。明确配套文件优先于 TTML 自带翻译，便于用户覆盖。翻译失败不应丢掉已成功解析的原文；可继续尝试兼容翻译输入或明确标注的内置翻译。

独立文件本身没有配对身份信息。沿用同目录同名约定后，还应检测时间轴是否可匹配；匹配不确定的行保持无翻译，不按行号硬拼。详情编辑器可以预览关联结果。

### 5.3 来源策略

第一阶段尽量保持已有可见选择：本地旁挂优先，旧缓存两组按迁移选择规则归一化。新增规则是“有效本地／内嵌／缓存内容可用时先显示；在线自动获取仅在没有可用内容时进行”。这会取消库内播放时抢先联网寻找逐字歌词的行为，应作为明确行为变更记录。

手动重新获取可以越过已搜索状态，取回、验证后才替换持久化内容；网络失败保留原内容。若旁挂文件仍按规则优先，重新获取不能暗中覆盖或删除旁挂文件；编辑／导出操作负责明确的文件写入。

WebDAV 复用相同候选排序和翻译配对：一次目录列举筛选全部后缀，按需下载，不为每个后缀重复列目录。已有大小、超时、取消限制继续保留；远端仍只读。记录 ETag/修改时间用于校验缓存，避免仅在歌词数据库为空时才永远读取一次；缓存先显示，显式刷新或有界的新鲜度策略决定是否进行远端校验，不在每次进度更新时访问网络。重试和刷新受连接状态约束。

## 6. TTML 接入范围

issue 附件的实测结构：

| 附件 | 原文 | 翻译 | 发音 |
| --- | --- | --- | --- |
| [逐行 TTML](https://github.com/user-attachments/files/32505618/50.txt) | 27 个正文 p 节点，带 begin/end 和 itunes:key | 27 条 en-US subtitle，通过 for 关联 | 27 条 ja-Latn transliteration；本轮不显示 |
| [逐词 TTML](https://github.com/user-attachments/files/32552336/50.txt) | 27 个正文 p，450 个正文逐词 span | 同上 | 元数据还含发音时序；本轮不显示 |
| [双轨 LRC](https://github.com/user-attachments/files/32505452/50.txt) | 27 组相同时间戳的双行 | 实际第二行与 TTML 的罗马音相符 | 按本次补充排除这种输入组合 |

TTML 导入步骤：

1. 按 XML 根元素及命名空间识别，不仅依赖扩展名；显式调用 TTML 解析适配器。
2. 保留正文 begin/end、逐词时间、空格、段落及稳定 key。原文持久化为保留这些信息的独立 TTML 文本。
3. 通过 `translation/text@for → p@itunes:key` 先准确关联原文，再使用对应原文的开始时间生成独立逐行 LRC 翻译。保留译文正文和毫秒精度的行时间，不携带逐字标记、翻译行尾或 XML 元数据；原文 TTML 的时序仍完整保留。保存前验证这份 LRC 能与原文重新唯一关联；不同 key 具有相同起点等无法无歧义转换的输入保留源内容并报告诊断，不制造时间差或按顺序硬配。
4. 独立保存的原文与翻译各只承载自己的显示内容，避免将元数据再次拼进正文。源 TTML 文件不改写，之后可重新导入发音。
5. 若有多种翻译，仅按文件已声明的 `xml:lang` 优先选择与应用语言匹配的一份，匹配不到时取文件中的首个可用翻译；没有标记也不调用语言检测。`xml:lang` 只用于本次导入选择，不新增持久化语言字段，不因系统不是中文而丢弃已有 en-US 翻译。
6. 首轮覆盖两个附件所用的行／词时间、translation 引用和常见正文嵌套。帧／tick 时间、复杂布局、ruby、完整合唱渲染不作隐含承诺；不支持的输入给出诊断，或在确实可保留正文时降级。

已有 `TtmlParser` 可作为基础，但不能把其“返回了 Lines”当作完整支持证明。需核对正文与元数据隔离、translation 引用、显式行尾保留和未知时间表达式； XML 读取明确禁用外部解析并限制大小。其已有 `Pronunciation` 数据接口未实际读出这两个附件中的 transliteration，本轮不补发音显示。

不对 TTML 原文统一执行现有 `FixEndMs` 的覆盖和压缩：只有缺失行尾时才补齐，使用下一条严格更晚的起始时间／歌曲时长。保留合法重叠；滚动焦点与歌词实际有效时间是不同概念。`RenderLyricsLine.LoadFromLyricLine` 目前也用下一行起点覆盖结束时间，接入 TTML 时需一并调整。

## 7. 解析、翻译对齐与运行时所有权

- 输入归一化后，原文按实际格式解析，翻译固定按逐行 LRC 解析，每份内容只解析一次。TTML 导入时先使用 key 生成准确的翻译行时间；活动文档重读时按精确时间匹配，再做有上限且无歧义的近邻匹配。建议统一 100ms 上限，并明确它相对现有 LRC 50ms 容差的变化。按 key 建索引或按时间排序后顺序关联，避免每条译文全表扫描。不得复用同一译文匹配多个原文，也不得把两条译文覆盖进同一字符串。
- 没有时间或稳定标识的翻译不自动按行号附着，也不伪造 LRC 时间。保留导入源文本或用户编辑草稿、报告无法转换；显示原文仍可继续。
- 同一 LRC 的重复时间戳只作为原文解析边界处理，不推断第二行的业务角色。仍须防止非法时间区间，但不承担组合歌词正确显示的验收目标。
- UI 收到的是一次性发布的完整快照；播放进度、当前行、动画状态放在各自显示状态中。`TransLateText` 可以暂时作为兼容投影，不能成为第二份可写内容来源。
- 当前 `ReturnLyrics` 会清空上次返回的 `Words`，而 UI／桌面渲染仍可能持有这些对象。建议取消跨发布快照的对象池复用；仅在未发布的解析临时对象上考虑池化。没有测量，不承诺零分配或具体收益。
- 保留请求代次、切歌取消、应用退出 token；发布前在 UI 线程再次核验代次和停止状态。取消后观察实际任务完成，再释放 CTS 与依赖。
- 保存还需比较 `Revision`，防止自动下载、详情编辑、扫描或手动刷新互相覆盖。只对歌词列做定向更新，避免整行写回旧 `Music` 覆盖收藏、偏移或统计。
- 将 `music.PlayCount++` 从歌词解析移到已确认开始播放的统一播放路径，按一次真实播放事件去重；重新解析、切换显示设置和手动刷新都不能增加次数。与已有播放历史统计明确区分。
- 解析缓存只保留当前／有界最近结果，以内容指纹、解析器版本、必要的对齐参数为键；显示翻译开关不重新下载、写库或解析原文。

## 8. 旧数据迁移

### 8.1 整对选择，不做空值拼接

旧行的两个候选仅用于迁移：

```text
A = (Krc, TKrc)
B = (Lyrics, TranslatedLyrics)
```

“有效”指非空白且内容可解析出有效原文，不是仅做 `IsNullOrEmpty`。格式靠内容探测，与旧列名无关。

| 旧行情况 | 新版活动内容 | 保留策略 |
| --- | --- | --- |
| 只有 B 有效 | B 原文＋B 翻译 | 旧行原样保留 |
| 只有 A 有效 | A 原文＋A 翻译 | 不因列名把格式写死成 Krc |
| A、B 都有效 | 默认 A，保持旧播放优先次序 | B 保留为迁移恢复数据，可在详情中一次性选择恢复 |
| A 无效、B 有效 | B | A 原始内容不丢弃 |
| 两份均非空但都不能解析 | 保留优先候选原文，标记 Unknown／解析诊断 | 完整旧行保留，可回退其他来源；不能标成在线 NoResult |
| 只有翻译无原文 | 不自动匹配其他来源的原文 | 旧翻译保留在恢复数据中，等待显式处理 |
| 全空或不存在旧行 | 创建明确空状态或按需新建 | 不制造“已确认无歌词”的搜索结果 |

优先候选无翻译时，默认也不借用另一候选的翻译。可以以后提供预览后确认的导入操作，本轮不自动跨版本合并。迁移前后所有非空旧字符串均应能从旧表／备份逐字恢复。

整对选择后，额外归一化所选翻译：有效的普通 LRC 可直接沿用；逐字或 TTML 翻译按行提取完整文本和开始时间，转为逐行 LRC。译文不含有效时间且无法借助明确引用关联时，迁移有效原文、保留旧译文在恢复数据中并记录诊断，不把未知格式文本写进约定为 LRC 的新字段。迁移报告需能区分“原本无翻译”和“翻译转换失败”，不能静默丢失。旧表备份仍保留转换前的全部内容。

### 8.2 数据库步骤

1. 使用 SQLite 一致性备份方式保留升级前数据库，正确覆盖 WAL；不要直接复制仍在写入的主 db 文件。
2. 初始化时只建新表、索引和迁移状态，不在启动 UI 线程解析整库歌词。
3. 先将所有生产写入口统一到新仓储，再开启新结构读取。禁止扫描或待写标签任务继续直接 `InsertOrReplace` 旧歌词表。
4. 读路径：新表有行就以新表为准；没有才读取旧行，通过适配器选出一对并迁入。新表空行也是有效状态，不能因文本为空就从旧表复活用户已经清空的歌词。
5. 每首歌在后台先解析旧快照，再开短事务：重验旧行指纹、新表仍不存在，写入新行与迁移状态。发生并发修改时重读重试，不在事务内做网络或文件解析。
6. 按小批次完成剩余迁移，保存进度；唯一主键与条件插入保证幂等。崩溃／断电后继续未完成记录，单首失败不阻止整库启动。迁移任务纳入 ApplicationTasks 的取消与退出排空。
7. 用户编辑、自动刷新、手动刷新使用条件更新比较 Revision。冲突时自动结果放弃覆盖；用户操作保留待处理结果并报告冲突，不静默丢弃输入。
8. 删除歌曲、文件夹或 WebDAV 源时，在相同业务事务内处理新表、搜索状态以及仍保留的旧歌词行，防止留下孤儿或下次恢复已删除内容。

旧表至少保留一个兼容发布周期；确认所有调用者切换、迁移核对和恢复流程通过后，再单独安排清理。新版本不双写四字段，不把两套结构长期作为同等权威。

回滚边界必须诚实：旧版程序只能看到旧表快照，看不到升级后的新编辑。完全回滚依赖一致性备份／显式导出；如果允许降级后再升级，需比较旧行指纹，并在新数据已编辑时报告冲突，不能自动覆盖新数据。

### 8.3 一次性播放缓存

新 JSON 使用 `SchemaVersion + Path + Document + CachedAtUtc`，Document 与库内业务模型一致，不再包含 Krc/TKrc/Lrc/Trans 四字段。

- 读取无版本旧 JSON 时，复用同一整对选择规则。迁移期间将旧缓存副本放在有界的 legacy 子目录或独立备份，不以覆盖原文件来丢弃另一候选。
- 新文件用唯一临时名、同目录原子替换；按路径串行化写入或使用版本检查，避免多个任务共享固定 `.tmp` 文件。
- 保留路径校验、容量上限、失败不影响播放。未知的新版本 JSON 不当作损坏立即删除。
- `Music.Id <= 0` 始终不读写歌词数据库。固定盘导入后迁入库内时，统一仓储仅在库内尚无有效内容／用户编辑时接收缓存。
- `AppJsonSerializerContextHelper` 注册新 DTO，显式处理版本；不依赖运行时反射补齐序列化元数据。

### 8.4 搜索状态与待写任务

`IsLrcSearched/IsKrcSearched` 不能直接合成一个布尔值：它们实际混合了提供方、逐字能力与是否尝试过。改为独立搜索状态记录，键包含曲目、提供方／请求类型以及匹配元数据版本。

新请求区分 Found、NoResult、TransientFailure；取消不记录成无结果。断路器按提供方或明确请求通道管理，一家故障不拦住另一家。自动获取关闭时不启动新网络任务，并取消其正在执行的自动请求；手动获取仍保留明确入口。

迁移旧布尔值时保守映射成对应旧请求范围的 LegacyCompleted，保留抑制重复请求的行为；不能声称已知具体提供方返回 NoResult。显式重新获取和匹配元数据变化可失效该状态。若以后增加无结果缓存 TTL，应另行定义默认值，不借本次合并悄悄改变它。

`PendingMetadataWrite` 的待写快照也需要版本化迁移。队列里已保存的歌词是当时用户编辑的快照，不能在执行时改读“当前歌词”替代。替换 DTO 前保留原队列内容，重启和文件仍被占用时都能恢复。

## 9. 文件导出与界面适配

- 详情页从四个内容区收敛为“歌词／翻译”两个内容区；原文显示实际格式，翻译明确标为逐行 LRC，无语言字段或翻译格式选择。状态、保存、重新获取和导出命令移到专用 ViewModel，保持当前布局习惯。
- 所有歌词保存 API 接收完整 `LyricsDocument` 与 expectedRevision；去掉含四个位置参数的接口，减少原文／翻译传错位置的可能。
- 普通保存时原文按真实格式写文件，翻译固定写 `_Translated.lrc`；用户选择“将原文导出 LRC”时才转换原文。TTML 原文的逐词时间转普通 LRC 会损失信息，导出流程说明这个选择的影响。翻译归一化为行级文本属于标准契约，不再为它提供逐字导出选项。
- 原文、翻译单独写入。两份文件无法天然组成一个原子替换：先生成并校验两个临时文件，再有备份地提交；中途失败报告哪一份成功，保留恢复文件。所有 I/O 被等待并观察，移除现有未观察的 `Task.Run`。
- 标签写回、音频转换和 USB 导出统一使用导出器。目标标签不支持 TTML／独立翻译时，仅输出兼容的原文表示，完整内容仍保存在数据库或独立文件中；不能把任意 TTML 文本直接塞进要求 LRC 的流程。
- 主界面普通／高级歌词、桌面普通／逐字歌词均验收同一原文和翻译。未来加发音时再为这些投影增加一份附加文本，不回到按歌词格式扩展 UI。
- 新增文案遵守项目独立 GetString 资源键要求，全部语言资源逐一核验。实现产生用户行为变化时在 `docs/Changelog.md` 顶部统一记录；本设计文档本身不记功能变更。
