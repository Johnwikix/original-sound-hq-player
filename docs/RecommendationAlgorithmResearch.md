# 本地音乐推荐算法调研与实现

更新：2026-11-03。对应本轮「TF-IDF内容近邻＋音频余弦近邻」更新。本文区分开源方法、项目自己的召回策略、实际测量与尚未证明的效果。随后追加的换批随机重排、近期曝光持久化及7天过期、Instrumental版本降权见下文；已有离线结果不能直接代表该追加版本。

## 结论与适用条件

本项目只有当前设备用户的曲库、收藏、歌单和收听记录，不能将一行用户交互矩阵当成充分的协同训练数据。本轮采用无需训练模型或额外运行时的内容item-kNN与音频item-kNN，再用RRF融合独立召回名次。实现为C#，支持NativeAOT，不引入Python服务、模型权重或新的NuGet依赖。

收藏/用户歌单继续提供正向训练证据，展示时改为软降权：主推荐、轮播、侧卡及跨流派探索使用0.1系数，降低90%排序权重；同名副本沿用保守的同名组规则。候选不足时仍可出现。最近常听完全不受此降权影响，也不将收藏常听移去凑主栏数量。

这不是「所有启发式都被消除」：近邻数、样本上限、来源内召回门槛、RRF常数、收藏系数和最终多样性约束仍是明确的工程参数，不能视为经过大规模训练校准的最优值。

## 实际向量与评分

### 内容item-kNN

`Services/Recommendations/ContentKnnProfile.cs` 负责拟合与评分，生命周期仅限单次固定曲库快照。

1. 艺术家、流派分别作为独立词域；同名艺术家和流派不会碰撞。先去空白、占位值和大小写重复标签，采用二值TF，每首曲目对同一词的文档频次只贡献一次。
2. `idf(t) = 1 + ln((N + 1) / (df(t) + 1))`，将每首的稀疏向量做L2归一化。没有把文件名、歌名、歌词或封面当成语义embedding。
3. 从收藏、有效用户歌单成员和有效收听中做确定性加权蓄水池采样，最多64首有内容特征的正向种子。相同输入不因刷新随机换训练样本。收藏/歌单重叠只形成一次明确偏好。
4. 使用仅覆盖种子的词倒排项，计算候选与种子的稀疏余弦；不构造N×N相似度矩阵。排除候选自身，取余弦最高的5个正向近邻。
5. 累加 `余弦 × 偏好强度`，除以全体种子中最大5个权重之和。这一分母对所有候选相同，只做缩放；不会因某个候选只匹配一个种子，就把它归一化成与多个稳定支持相同的分数。
6. 解释来自实际近邻共享的艺术家/流派词。专辑用于展示去重和多样性，不再将同专辑或同年代本身当成个性化风格证据。

### 音频item-kNN

`Services/AudioAnalysis/AudioPreferenceScorer.cs` 继续按64行分页，三遍读取SQLite：曲库尺度统计、校准后的正向种子收集、候选评分。`AudioNeighborProfile.cs` 替代旧的8中心聚类；相似度与聚合规则与内容近邻一致，最多64个128维种子、5个近邻，排除自身。

提取器和缓存格式不变，无需重新分析文件。每首20%/50%/80%附近各10秒，共保存384个float。片段先做逐维曲库均值/标准差校准和L2归一化，再平均并L2归一化。至少16条有效分析才启用音频评分。

| 128维位置 | 输入 |
| --- | --- |
| 0–39 | 20个MFCC的均值/标准差 |
| 40–55 | 8种频谱形状统计的均值/标准差 |
| 56–67 | 6频段对比的均值/标准差 |
| 68–79 | 6种移调不变音级间隔统计的均值/标准差 |
| 80–111 | 16个相对log-mel频带的均值/标准差 |
| 112–123 | 12个起音自相关节奏带 |
| 124–127 | 4个动态/静音统计 |

这是低层声学相似度，不是经过训练的语义流派分类。逐维标准化也会改变提取器原有组先验的效果，不能把原组系数当成最终推荐占比。

### 正向证据与融合

有效收听仍使用最近90天、至少播放50%的会话。每次以完成比例除以 `1 + 距今天数/30` 后求和；种子强度为 `min(3, ln(1 + 收听权重)) + 2 × 是否收藏或歌单成员`。未听过不表示不喜欢。

每个来源保留最多200个候选，先按软降权后的来源分排序，防止大量收藏挤占有限召回池。对有变化的已知来源分数，优先召回高于该来源本批均值的非收藏候选；未知音频不进入音频均值，已知的0相似度会进入。单条或平坦正向来源保留可用结果，不设固定绝对余弦下限。收藏项不因均值门槛被硬排除。这是本项目的背景中心化召回策略，仍需更大样本验证。

RRF为每个命中来源累加 `1 / (60 + rank)`，rank从1开始。按本批最大RRF分统一缩放后，对收藏/歌单及同名项乘0.1，标题含Instrumental（忽略大小写）再乘0.25；来源缺失时没有加权均值分母，也没有重新制造缺失0分。解释取贡献名次最高的实际来源。Last.fm仍消费现有只读快照，不增加网络请求或远程播放地址。

保留主推荐、最近常听、换个流派听听的独立用途。跨流派探索要求有效不同流派证据，以流派陌生度排序；已听项权重乘0.5，收藏/歌单项再乘0.1，允许已听曲目回听，不受主推荐的相关性下限约束。累计播放次数或最近有效收听任一显示已听即应用降权。全页继续按ID和完整艺术家＋歌名去重。没有来源证据时使用有界、可复现的随机回退，同样降低收藏项权重。

| 参数 | 当前值与性质 |
| --- | --- |
| 正向种子上限 / 每候选近邻数 | 64 / 5；控制资源与兴趣支持，未证明最优 |
| 来源窗口 / RRF常数 | 200 / 60；RRF常数沿用常见默认值，窗口保留少数兴趣覆盖 |
| 收藏展示系数 | 0.1；用户要求大幅降权，训练和常听不受影响 |
| Instrumental版本展示系数 | 0.25；标题忽略大小写子串匹配，作用于所有推荐栏目并参与有界召回；与既有展示系数相乘，不改变训练 |
| 跨流派栏已听系数 | 0.5；取消未听硬门槛，已听且收藏时合计0.05，常听不受影响 |
| 主栏 / 常听 / 探索上限 | 各20；轮播5、侧卡3，候选不足时减少独立项 |
| 最终主推荐多样性 | 当前最佳展示亲和分的相对12%窗口，沿用歌手/专辑约束；展示分乘 `1 + 0.12 * 批次随机值`，不是概率校准 |
| 近期曝光 | 最近三个未过期批次的展示分与展示亲和分分别乘0.15/0.35/0.6，同录音版本共享；首次展示7天后失效，重启不续期；作用于各推荐栏目，不改变训练、来源名次或有效收听基础评分 |
| 重启批次 | SQLite保存下一批次与三批有界ID/UTC曝光快照，恢复时清理过期记录；只提交已展示结果，不保存Music、评分或播放队列 |

## 本地对照与失败记录

### 数据与防泄漏

使用 `SnapshotData.py` 以SQLite在线backup从只读源创建快照，包含WAL已提交数据；原库、设置和特征库没有被修改。库和特征分别备份，未宣称跨两个数据库的原子快照。当前实际快照为232首曲目、133个收藏/歌单正向同名组、232条当前版本特征行；不能与旧文档的7,281首历史数据混为同一评估。

快照标识：library SHA-256 `e4f84194a172d6a732e7b178672cd0727bff43280d8e5b87918307df32fac837`，features SHA-256 `14f5f9c8e66edb1ca61dc47ac9d60840b5b316ec77d98381f09a3a4a912b7522`。

- 按去空白、忽略大小写的完整歌名组做5组留出；这是保守同名组，不声称完成录音身份识别。一个组的全部副本同时隐藏收藏、歌单、收听及累计播放证据。
- 每组运行3个批次，共15次查询。标签只用于统计，不进入拟合。以下Recall/NDCG按查询取宏平均；命中次数包含跨批次重复，不是独立用户或独立命中数。
- 主栏20项单独评估；轮播＋侧卡＋主栏合计最多28项另报命中。随机/收听基线直接取前20项，旧版和新模型使用相同栏目分配入口。旧版冻结自 `f1455f32`，保留其原硬排除政策；新模型按用户最新要求软降权，比较同时包含模型与政策变化，不能全部归因于某一算法。
- 所有模型都假定曲目可播放；没有模拟真实WebDAV离线状态。社区来源全部关闭，因为缺少可复现且时间有效的社区快照。

### 未通过与未解决的场景

完整快照检查曾被遗漏：实际232首曲目中231首已有累计播放记录，唯一未听曲目没有流派标签。此前保留「从未听过」门槛，导致完整输入的3个批次均只有主栏20、常听20、探索0；留出评估清除了部分曲目的收听证据，反而制造出了探索候选，不能证明真实首页第三栏可用。现已取消该门槛，仅降权；同一完整快照3个批次均恢复为20/20/20，并将完整输入栏目计数写入评估报告，新增全已听的真实WinUI回归。

第一版使用最近5个匹配种子的逐候选加权平均，支持数被抵消；40项来源窗口还可能丢掉少数兴趣。该版主栏Recall@20为0.3416，低于旧版0.4606，因此没有直接作为最终版本。仅扩窗口和均值门槛仍只有0.3074，说明问题不能靠调窗口掩盖。修正为加权求和、共享缩放后，硬排除阶段为0.4630 / NDCG 0.6264；最终再按用户要求改为收藏软降权，得到上表结果。

另做14天时间留出：移除所有当前收藏/歌单标签，避免使用缺少历史时间戳的未来信息；只用截止日前90天的有效收听训练，目标为未来14天出现且训练窗口未出现的5个新同名组。3个批次中所有模型主栏命中均为0；旧版含精选命中累计3次，新版为0。新曲的时间泛化没有得到验证，仍是明确盲区，不能用分组留出的改善掩盖。需要更多带曝光时间、独立负反馈和完整历史的数据再评估。

## 验证与复现

基线源码冻结在 `_tools/HomeRecommendationRegression/Baseline`，不进入主程序编译或分发。评估报告与私有曲库快照留在被忽略的 `artifacts/recommendation-knn-snapshot`；文档仅保留汇总数字与快照摘要。

```powershell
python _tools/HomeRecommendationRegression/SnapshotData.py <MusicDatabase.db> <Features.db> <新快照目录> --settings <Settings.json>
dotnet run --project _tools/HomeRecommendationRegression -- --evaluate <快照目录>
dotnet publish _tools/HomeRecommendationRegression -c Release -r win-x64 -p:PublishAot=true -o artifacts/recommendation-knn-native
artifacts/recommendation-knn-native/HomeRecommendationRegression.exe
artifacts/recommendation-knn-native/HomeRecommendationRegression.exe --evaluate <快照目录>
```

本次第三栏修复已执行：推荐回归118项（JIT与Release/win-x64 NativeAOT）、真实WinUI偏好与绑定25项、栏目分配14项，以及完整原始快照3批次栏目计数。主项目Debug/x64构建通过，有未清理的构建警告。音频算法未改动，沿用前轮8项音频偏好和24项worker/SQLite/取消/缓存租约集成证据；未重复完整历史播放/上报回归或真实设备听感验收。
