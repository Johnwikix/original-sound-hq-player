# 启动后台扫描

启动只等待数据库中的音乐库、播放状态和音频服务恢复。主界面进入 Ready 后，StartupCoordinator 持有一次后台扫描任务；仍使用 LibraryOperationGate 与手动维护、目录监视扫描串行执行。

标题文字右侧显示启动扫描进度环和百分比。枚举文件确定总数期间显示不定进度与“…”；随后按已检查文件数更新（包含无需重读元数据的未变更文件），整百分比变化才发布 UI 通知。路径快照直接供扫描复用，不重复遍历目录。最后的去重与 UI 刷新阶段保持最多 99%，整个任务结束、失败或取消时隐藏；不影响 LoadingGrid 的现有显示条件。

扫描只更新数据库，完成或部分失败后在 UI 线程刷新音乐库。不会再次调用 LoadMusicList、GetPlayStateAsync 或 InitializeMusic，所以不会恢复旧音量、切回上次歌曲或重置正在播放的进度。队列保持现有顺序（包括随机顺序），更新非当前歌曲的记录，剔除已从库中删除的非当前歌曲；新增歌曲在音乐库显示，不擅自加入队列。当前歌曲对象保留到用户切歌，避免打断正在使用的音频流。

离线或无法完整枚举的目录仍保留记录。退出取消信号贯穿扫描与批次提交，未完成枚举不推断删除；清理等待扫描工作实际结束后才释放依赖。正在执行的同步文件/元数据读取无法强制中断，退出可能仍需要等待该次 I/O 返回，此项不代表 TODO 第四项的全部退出问题已解决。

后台 SQLite 物化 Music 时不再触发歌词偏移发布或整行写回；用户在 UI 中修改偏移只更新该字段。

## 验证

- `dotnet build WinUIMusicPlayer.csproj -p:Platform=x64 --no-restore -v:q`
- `dotnet run --project _tools/FolderScanRegression --no-restore`：真实 SQLite 扫描、变更检测、离线目录保护、取消后等待在途读取、禁止迟到提交和误删、重试，以及队列顺序/当前对象/集合通知。
- 回归中的 UI 使用适配桩，不能替代 WinUI 和实际音频播放验收。

## 待实机验收

1. 大音乐库或慢盘启动：未扫完即可浏览缓存库并播放，扫描完成后新文件出现。
2. 扫描期间播放、暂停、切歌、改音量、改歌词偏移、切换随机模式：完成刷新后保留用户状态。
3. 启动前增删文件、修改标签、断开外置盘：正确更新可访问目录，不清空离线目录；当前播放不被刷新打断。
4. 空缓存但已有目录配置：扫描后歌曲出现并可双击播放。
5. 扫描期间退出与快速重新启动：无退出后的集合通知或后台写库；慢盘需记录最后一次读取的等待时间。
