# Last.fm 接入

本播放器使用用户自备的 Last.fm 应用凭据，不内置开发者 API Key，也不要求用户把 Last.fm 密码交给播放器。

## 使用

1. 在“设置 → 常规 → Last.fm → 应用凭据”打开“申请凭据”，登录 Last.fm 并申请 API Key / Shared Secret。
2. 填入两个值，点击“保存凭据”。Secret 留空且 API Key 不变时，继续使用已保存的 Secret。
3. 点击“连接账号”，在浏览器允许访问，然后回到播放器点击“完成授权”。采用桌面 Token 授权，无需播放器协议回调。
4. 授权成功后自动启用上报。关闭开关会暂停新记录和已有队列的发送，重新开启后继续补报。
5. 展开“本地播放历史”，点击“补报本地历史”，手动上传原来已经保存的本地播放记录。默认只补报最近 14 天；可开启“允许按导入当天补报更早历史”。此操作需要已连接账号、开启上报并联网；不会因启动、授权或点击“立即重试”而自动执行。
6. “解绑”清除本地 Session Key 和待补报记录，保留应用凭据。要撤销 Last.fm 服务器端权限，使用“管理 Last.fm 应用授权”。更换应用凭据也会解绑并清空队列。

## 补报原有本地历史

- 手动读取现有 SQLite `PlaybackHistory`，不修改、删除历史或重新计算本地统计。只读取已经结算入库的会话，正在播放且尚未入库的会话不在本次导入中。
- 默认只读取最近 14 天，按每条记录原始 UTC 开始时间提交。“允许按导入当天补报更早历史”默认关闭，每次启动及切换账号/凭据后恢复关闭；仅改变手动导入，不会自动触发上传。
- 开启选项后，超过 14 天的合格记录改用导入时本机当天已经过去的秒数，避开远端已有记录、已成功上报缓存及现有队列占用的时间。同一首歌的多次历史播放分配不同秒数，不生成未来时间；当天已过去的可用秒数不足时暂缓其余记录，稍后再手动补报。
- Last.fm 会将这些旧记录计入导入当天的统计。本地数据库原始开始/结束时间、收听时长和统计保持不变；队列同时保存源记录标识、原开始时间与分配的上报时间，离线重试及重启沿用已经分配的时间，不重新改成重试当天。
- 界面显示入队、其中改用导入当天、已存在、过旧未导入、不达标/信息缺失和暂缓的数量；入队不等于服务器已接受。
- 大于 30 秒且收听时长达到一半或 4 分钟的记录才参与补报；同时以开始至结束的墙钟时长限制旧统计中的定位跳变量。旧统计没有逐次暂停/定位明细，无法完整重建实际收听，实时上报继续采用原来的独立会话口径。
- 先通过 `user.getRecentTracks` 分页核对当前账号记录，再与待发送队列及已成功上报指纹核对，减少旧版本已上报记录被重复导入。按规范化歌名、歌手和开始时间匹配，容忍本地统计与解码确认最多 10 秒差异，每条已有记录只匹配一次；服务器自动纠正元数据或超出此时间差时仍可能无法识别同一播放。
- 已成功上报缓存绑定应用凭据和账号，保留最近 14 天、最多 100,000 条；另存不按时间过期的导入去重标记，按账号和源记录标识去重。源标识取本地历史行 ID 与原始 UTC 精确时间的指纹，同一事件后续修改歌名不改变标识，同一首歌的不同播放仍分别导入。
- 源标识、原始时间、分配时间与曲目快照在发送前与队列同一次 SQLite 事务提交。分配记录独立于发送队列保留，解绑/更换凭据清空队列后，同账号再次导入先按分配的准确时间核对远端，仍在有效期内的未确认记录沿用原分配时间和曲目快照。当天尚未确认的旧分配也继续占位，避免其他源记录重复使用同一秒。
- 收到明确成功响应后，永久去重标记与队列清理在同一事务提交。落盘失败时保留完整内存确认；解绑、换号、更换凭据或正常退出前先尝试保存确认，保存失败不把该条确认丢弃。不同账号的去重标记独立。
- 改用导入当天的上报时间仅参与时间占位及源记录的准确核对，不参与真实原始播放的 ±10 秒模糊匹配，避免吞掉同一首歌当天真实发生的播放。历史分页每次请求后释放网络槽位，分页间隔不阻塞正在播放或离线队列发送。夏令时午夜重复时选择当天最早的有效 UTC 起点。
- 长期标记最多 500,000 条（包括未确认的分配记录），达到上限暂缓新导入，不淘汰旧标记。去重标记存储于 SQLite，按主键增量写入，不再随每条播放全量重写或常驻内存；源记录查询每批最多 500 个键。
- 首次启动将旧 `LastFm.json` 事务迁移到同目录的 `LastFm.db`，旧 JSON 保留不改，初始化成功后以数据库为准；迁移失败不会写入空状态。首次迁移仍需读取旧文件，后续启动不加载长期标记。旧版成功标记没有保存源记录到上报时间的对应关系，无法可靠还原：相关模糊命中显示为“旧版映射不明、待核对”，暂缓而不误记成功。删除数据库或更换不保留行标识的历史数据库会丢失对应去重依据。
- 本地查询每页 500 条，远端每页 200 条；单次暂存至多 100,000 条未处理候选，优先最近 14 天的记录；已导入条目不占候选容量。最多核对 500 页远端记录；开启更早历史时，查询范围向前扩展至本次最早候选，以识别原日期已经上报的旧记录。超过候选容量的记录显示为暂缓，远端核对超过上限或失败则不提交导入；队列满时保留已有记录并报告暂缓数量。
- 导入按时间排列后追加到现有队列，保留已有队列顺序及其在途确认。网络核对期间新播放仍可持久入队；只有完整核对、原子保存成功后才发布导入结果。可取消核对/准备过程；已入队的记录继续由现有队列发送。

## 行为与边界

- 实际播放确认后发送 Now Playing；暂停、缓冲和未确认启动不会上报为新播放。Last.fm 没有清除 Now Playing 的对应接口，暂停后展示由服务端自然过期。
- 大于 30 秒的曲目，实际收听达到一半时长或 4 分钟（取较早者）后记一次 Scrobble；Unix UTC 时间戳取本次播放开始时刻。
- 独立于本地播放统计，仅累计连续、推进中的引擎快照，并以单调时钟时间限制计入量。快进、后退、定位代次、重复快照、暂停、缓冲和无缝切歌边界不会贡献跳变的时间。
- 无缝重复同一曲目仍是新会话。WebDAV 断流后恢复原进度保留当前会话；手动重播建立新会话。
- 本地统计的门槛、入库和播放次数保持原实现。无有效歌名或歌手元数据的曲目跳过 Last.fm。
- 达标记录先事务写入 SQLite 队列状态，再发送。网络失败和限流采用退避重试，启动后自动恢复；按原顺序补报并保留原开始时间。Now Playing 不持久化补发。
- 队列最多 10,000 条，满时保留已有记录并提示。无法读取的队列不会被空状态覆盖；修复存储权限或内容后点击“立即重试”。
- 队列记录绑定 API Key 与账号名称。授权失效时暂停发送，为原账号保留记录；重新授权其他账号不会继承旧账号队列。
- Last.fm 返回的 accepted / ignored 会被区分；不可修复的元数据或过旧记录会被跳过并提示，失效 Session Key 则要求重新授权。
- 持久化重试不能保证服务端严格去重：若服务端已接受请求但响应在途中丢失，或成功响应后持久化始终失败且进程被强制结束，自动离线重试仍可能重复。手动重新导入历史会使用保留的分配映射核对远端；服务端数据延迟、元数据纠正和其他客户端的记录也会影响核对结果。

应用凭据和 Session Key 存储于 Windows PasswordVault 的 `OriginalSoundPlayer.LastFm` 资源。非敏感偏好、待补报元数据及去重记录位于“文档/OriginalSoundPlayer/Settings/LastFm.db”；该数据库不含 Shared Secret 或 Session Key。旧 `LastFm.json` 仅保留为迁移备份。

## 实现与验证

- `Services/LastFm`：签名 HTTPS API、凭据边界、SQLite 事务队列、生命周期、会话资格与播放观察。
- `LastFmSettingsViewModel`：设置草稿、命令、忙状态与 UI 线程通知；视图只绑定现有 ViewModel。
- `PlaybackCoordinator` / `RemotePlaybackService`：新增实际播放确认通知，不改变音频引擎或 IPC 协议。
- `_tools/LastFmRegression`：生产核心代码 + 真实本机 HTTP / SQLite 事务持久化，使用虚构凭据。
- `_tools/LastFmUiRegression`：生产 XAML、ViewModel、会话观察桥及真实 WinUI 调度/绑定；音频与 Last.fm 服务端为异步边界夹具。

真实 Last.fm 账号授权、服务器接收结果与完整播放器在真实设备/WebDAV 服务器上的长时间试听仍需具备用户凭据后验证。

本次验证：101 项核心回归、30 项真实 WinUI 检查；关闭 JSON 反射回退的裁剪发布及 NativeAOT 发布各通过 514 项检查，覆盖真实 SQLite 行映射、事务存储、源生成 JSON、分页及取消。新增回归覆盖改写时间与真实播放分离、成功后写入失败再解绑/换号并重启、跨天分配保留、旧版迁移、分页期间实时发送和夏令时重复午夜。主程序 Debug x64 构建通过；七种语言的取词键与格式占位符检查通过。UI 布局与 MVVM 边界保持现有实现。

性能夹具使用独立 SQLite 数据库、10 万条长期标记及空发送队列，预热后 5 次状态保存累计托管分配约 10 KB，重新打开约 10 KB；12 页远端核对期间，正在播放请求约等待 2 ms。这些是该夹具的观测值，不代表完整播放器内存、磁盘实际写入量或真实 Last.fm 网络延迟。已有发送队列仍按上限 10,000 条保存状态 JSON；其序列化开销随队列大小增长，长期标记不再加入该文档。首次大 JSON 迁移和大规模手动核对属于冷路径，仍有一次性工作与有界候选/索引内存。队列验证、序列化及索引准备在后台完成，避免暖提交回到 UI 采样线程。

可重复执行：`dotnet run --project _tools/LastFmRegression -c Release`；裁剪/AOT 发布命令见 `_tools/LastFmAotRegression/README.md`。高对比度、真实 Last.fm 账号和真实设备/WebDAV 长时间试听未执行。

官方参考：[桌面授权](https://www.last.fm/api/desktopauth)、[Scrobbling 规则](https://www.last.fm/api/scrobbling)、[track.scrobble](https://www.last.fm/api/show/track.scrobble)、[user.getRecentTracks](https://www.last.fm/api/show/user.getRecentTracks)。
