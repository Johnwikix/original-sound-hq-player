# 文件夹扫描链路修改计划与验证记录

日期：2026-09-15。本文对应本次修订后的实现，替代先前未提交改动中的扫描方案。

## 问题与原因

| 问题 | 定位结果 |
| --- | --- |
| 扫描完才一次性出现歌曲 | 原扫描器先 `Task.WhenAll` 等待整个目录，再遍历结果切批；目录内一个慢文件即可挡住全部结果。 |
| 重扫、移除按钮仍可点 | `FolderCommands` 没有 `CanExecute` 条件；VM 内虽然检查了 `IsScanning`，但维护操作自身没有完整持有忙碌状态。选择器、确认框也在互斥范围之外。 |
| 文件夹计数一直显示 0 | `MusicBrowseViewModel` 提前解析 `AddFolderViewModel` 时，`SongsSource` 尚未加载；计数依赖了空内存列表。`SongCount` 的 `x:Bind` 又默认为 `OneTime`。旧数据库中的 `Folder.SongCount` 也不能作为真实数量。 |
| 分配和刷新开销 | 每个文件创建任务，递归目录继续并行放大任务数；目录结果、全库元数据、UI 待刷列表重复积累。每个 UI 批次还重新排序整库并滚动到播放项。 |
| 重扫写入和删除风险 | 旧元数据更新先排队修改对象，随后立即写库，存在写入旧值的时序问题；路径 `Contains`/裸 `StartsWith` 混淆同名前缀目录；不完整枚举可能被当作删除依据。 |
| FFmpeg 兜底不完整 | Windows 属性读取抛异常会跳过 FFmpeg；主分支失败后重复创建 ATL Track；探测没有大小、数据包数或时间边界。 |

## 修改计划及落地

1. **先建立反馈回路。** 使用可控的慢文件测试首批输出，保留 `--legacy` 重现原来的整目录等待；将真实扫描器、数据库扫描 partial、VM 和命令链接到控制台回归项目。
2. **有界扫描核心。** `ScanPipeline` 使用 4 个长期工作任务，一个受锁保护的惰性路径枚举器，容量 128 的结果 Channel，以及一个串行批次消费者。消费者失败时取消并等待生产者结束。暂存上限为消费者批次 128 + 排队结果 128 + 4 个工作者；不包括最终曲库、路径索引和单文件解析器自身内存。
3. **批次事务与 UI。** 每批最多 128 首；首批立即发布，后续有 UI 回调的批次间隔至少 500ms。歌曲和可补充的内嵌歌词在同一事务提交后，才等待 UI 应用。移除第二套定时器和无界 UI 缓冲。歌曲列表追加有限数量的单项通知，避免每批 Reset、全库排序和自动滚动；完成后统一整理排序、分组及播放列表映射。用户主动切换排序/视图仍按既有刷新逻辑处理。
4. **统一互斥范围。** 添加、拖入多个文件夹、重扫、移除覆盖选择器/确认框到最终刷新全过程；命令禁用与方法入口检查同时生效。启动扫描、文件监视扫描使用同一个操作门；自动扫描等待手动操作释放。
5. **共享数据库扫描实现。** 移入 `MusicDatabaseService.Scanning.cs`。添加仅查询现有路径；扫描中在事务内复核去重。重扫只写元数据字段，保留收藏、排序、播放次数、歌词偏移及已有歌词。启动按修改时间读取变化文件，避免逐文件遍历整库查找。目录枚举失败不执行该次重扫的删除阶段；自动扫描成功后才推进目录时间戳。
6. **数据库计数。** 从 `Music` 按实际目录分组汇总，再合并到所管理的根文件夹。忽略持久化的旧 `Folder.SongCount`，不依赖 `SongsSource`。操作结束重新查询，加载版本号阻止过期查询覆盖新扫描的文件夹行。`SongCount` 使用 `OneWay` 绑定。
7. **兜底读取。** 保留 ATL 主路径；复用已经取得的 Track，Windows 属性失败后仍可独立进入 FFmpeg。FFmpeg 限制为本地文件协议，1 MiB 探测量、128 个探测包、2 秒媒体分析时长及 5 秒协作式中断回调。仅补缺失技术字段，保留 DSD 位深语义。

## 验证

运行：

```powershell
dotnet build WinUIMusicPlayer.csproj --no-restore --disable-build-servers -p:Platform=x64 -p:Configuration=Debug -nr:false
dotnet run --project _tools/FolderScanRegression --no-restore --disable-build-servers
dotnet run --project _tools/FolderScanRegression --no-build -- --legacy
```

`--legacy` 应以“slow file blocks all batches”失败退出。新版应通过：

- 首批在慢文件完成前到达、尾批不丢失、批次容量和刷新间隔。
- 慢消费者下积压有界；回调失败、取消后工作任务全部收尾。
- 真实 SQLite 的先提交后发布、歌词事务回滚、去重及文件夹边界。
- 真实 VM/命令的添加、重扫、移除禁用，以及直接调用、选择器和确认框竞争。
- 旧数据库已有歌曲、`SongsSource` 为空时仍显示正确数量。
- 重扫保留用户状态和歌词，启动跳过未改文件，离线根目录保留旧记录，纯删除扫描报告变化。
- 真实 FFmpeg DLL 读取中文路径 PCM WAV，校验采样率、声道、位深、时长；损坏文件、不存在文件、网络输入安全返回。

调度微基准使用 100,000 个合成结果，不含 ATL、SQLite 和 WinUI。一次测量中，旧任务列表分配 14,001,448 B，新版固定工作任务分配 945,520 B，减少约 **93.2%**。耗时分别约 19.6ms、36.4ms；这个无 I/O 场景中新版不更快。其收益是减少调度分配和峰值积压、尽早输出，并非承诺整库扫描加速或整体 GC 降低同样比例。实现过程中曾测到 `Parallel.ForEachAsync` 版本分配更多，已用固定工作任务替换。

## 验证边界

- 回归项目使用真实 SQLite、生产扫描/VM/命令代码和真实 FFmpeg；WinRT 文件、ATL 元数据及 Dispatcher 使用适配器。尚未完成真实 WinUI 窗口的滚动、选择、多页面导航及整库 GC/帧时间测量。
- 分组与最终排序在收尾整理；扫描期间的歌曲列表暂按到达顺序追加。
- 为避免目录循环，扫描不递归进入重解析点；删除前另行检查文件及父目录，保留跳过的现存文件和重解析点下记录。目录访问失败会保留已提交批次并停止该次扫描，后续可重扫。
- FFmpeg 的 `find_stream_info` 可能读取并解码少量数据，并非纯头读取。中断回调属于协作式限制，不能保证中断任意阻塞的操作系统 I/O，也不提供进程隔离。[FFmpeg AVFormatContext 文档](https://ffmpeg.org/doxygen/trunk/structAVFormatContext.html)
- 没有用真实用户数据库执行测试或删除操作；不需要通过清库解决计数问题。未新增 `GetString` 资源键。
