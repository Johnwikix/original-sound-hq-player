# 添加文件夹链路改造：增量上架 + ffmpeg 兜底探测 —— 详细实现方案

## 目标

1. 去掉添加文件夹过程中的 ProgressRing 阻塞式反馈，扫描结果按批次渐进出现在 MusicBrowsePage / AddFolderPage（UI 刷新节流 ≥500ms）。
2. `GetAudioInfo` 失败后的兜底链补一级 **FFmpeg 头探测**（仅技术字段，不解析标签），同时消除现存的"双重 RetryOnFileBusy 最多 24 秒"问题。
3. 顺带解开 `ProcessRingVisibility` 被"空库添加"与"USB 传输/文件监视"共享的耦合（添加流程不再触碰该字段）。

## 现状回顾（改造依据）

- 链路：`AddFolderViewModel.AddFolderMusic` → `CheckFolderBeforeAdd`（[MusicDatabaseService.cs:1444](Services/MusicDatabaseService.cs#L1444)）→ `ScanFolderAsync`（:1390）→ `AddFolderService.GetMusicFilesRecursive`（[AddFolderService.cs:129](Services/AddFolderService.cs#L129)）全量收集 → 一次性 `InsertAllAsync` → `RefreshSongsSourceAsync` 整表重载 + `RefreshAllViews` 全视图重建。
- `GetMusicInfo` 主路径 ATL 失败后进 `GetAudioInfo`（[ToolUtils.cs:497](Utils/ToolUtils.cs#L497)），后者再次 `RetryOnFileBusy(new Track(...))` —— 对被占用文件叠加两轮各 ~12s 重试。
- 已有可复用设施：
  - `AppViewModel.RefreshDataForPageType(AppData.CurrentPage)`（[AppViewModel.cs:1048](ViewModel/AppViewModel.cs#L1048)）—— 只刷新当前页的轻量路径；
  - `Folder.SongCount` 是 PropertyChanged 属性（[Folder.cs:15](Model/Folder.cs#L15)），AddFolderPage 行内实时绑定；
  - 项目已内置 FFmpeg 9.0.1 DLL + FFmpeg.AutoGen（进程内、平铺 DLL 无需初始化），`External/AudioPlayer/Decode/PcmDecoder.cs:49-117` 是现成的"开容器→读流参数"模板；
  - `AddMusicList`（[MusicDatabaseService.cs:1853](Services/MusicDatabaseService.cs#L1853)）的 Channel+worker 是并发管线先例（本次不需要，回调式更贴合现有习惯）。
- 死代码：`GetMusicListByFolder`（MusicDatabaseService.cs:1383，全仓库无调用）与其依赖的旧 `GetMusicFilesRecursive` 唯一存活调用方就是 `ScanFolderAsync`，可安全重构删除。
- 必须保持签名稳定：`RescanFolderByPath` / `RescanFolderWithOutUpdateAll`（AutoRescanService、AppViewModel 依赖）；`ScanFolderAsync` 仅被 `CheckFolderBeforeAdd` 调用，可加可选参数。

## 核心设计决策

- **批次边界**：元数据按目录并行读（沿用信号量 8），每积累 **100 首**（`ScanBatchSize` 常量）即入库一次（`InsertAllAsync` 自带单事务、自增 PK 回填到对象）；目录结束时不足 100 的尾批也冲一次。
- **UI 节流**：批次回调不直接刷 UI，进入 AddFolderViewModel 的合并器 —— 一个 500ms 单次 `DispatcherQueueTimer`（`UIFlushInterval` 常量）：首批到达启动定时器，到点把累积批次一次性应用，之后有新批次再重启定时器。稳态刷新频率 ≤2Hz，与扫描快慢解耦。
- **渐进期只刷当前页**：UI 应用批次 = `SongsSource.AddRange` + 增量维护 `_idIndex` + 翻转 `LibraryEmptyVisibility` + `RefreshDataForPageType(AppData.CurrentPage)`。**不调用** `NotifySongsSourceChanged`（避免 RefreshAllViews 全视图重建）。专辑/歌手/文件夹分组索引与排序在渐进期是 stale 的，由**收尾一次全量 `RefreshSongsSourceAsync`** 修正（即时反馈与最终正确性兼得）。
- **空库占位切换零成本**：首批应用后 `SongsSource.Count > 0` → `LibraryEmptyVisibility=Collapsed`，占位自动让位给内容 Frame，无需额外逻辑。
- **AddFolderPage 反馈**：`CheckFolderBeforeAdd` 插入 Folder 行后立即回调（新文件夹行先出现），此后每次 UI 冲刷给该 `Folder.SongCount += 批内新增数`，行内数字实时跳动，替代原 Loading 遮罩。
- **重入保护**：`AddFolderViewModel.IsScanning`（Observable），`AddFolderCommand` 挂 CanExecute（CommunityToolkit `NotifyCanExecuteChangedFor`），静态 `FolderCommands` 的重扫/移除命令在 IsScanning 时早退。**重扫/移除保留原 Loading 遮罩**（低频维护操作，遮罩本身就是防重入）。
- **ffmpeg 兜底定位**：仅在 ATL + Windows 属性系统之后，数值字段仍缺失（时长/采样率/声道/码率）时做一次纯头探测；标签字段（标题/歌手/专辑/年份/音轨/歌词）维持现有来源，ffmpeg 完全不碰。

## 文件级改动

### 1. 新增 `AudioConverters/FFmpegMetadataProbe.cs`（~120 行）

`public static unsafe class FFmpegMetadataProbe`，唯一入口：

```csharp
public readonly record struct ProbeResult(int SampleRate, int Channels, int BitDepth, int BitRateKbps, double DurationMs);
public static bool TryProbe(string path, out ProbeResult result);
```

实现照抄 `PcmDecoder.Open`（External/AudioPlayer/Decode/PcmDecoder.cs:49-117）的头探测部分，不打开解码器：
- `avformat_open_input` → `avformat_find_stream_info` → `av_find_best_stream(AVMEDIA_TYPE_AUDIO)`，任一返回负值即失败（返回 false，调用方落到文件名兜底）；
- 采样率/声道取 `codecpar->sample_rate` / `codecpar->ch_layout.nb_channels`；
- 位深取 `codecpar->bits_per_raw_sample`（≤0 则置 0，不猜默认值）；
- 码率取 `fmtCtx->bit_rate / 1000`，为 0 回退 `codecpar->bit_rate / 1000`；
- 时长取 `fmtCtx->duration * 1000.0 / AV_TIME_BASE`，`AV_NOPTS_VALUE` 时回退 `stream->duration * av_q2d(stream->time_base) * 1000`；
- 所有路径 `avformat_close_input` 释放；无 Tag 读取；本地文件默认 probesize 上限足够，不额外设 analyzeduration。
- 线程模型：每次调用独立 AVFormatContext，与 FFmpegAudioConverter 并行安全（libavformat 上下文级隔离，AutoGen 为纯 P/Invoke）。

### 2. `Utils/ToolUtils.cs` — GetAudioInfo 改造（~20 行）

- **消除双重重试**：[ToolUtils.cs:501](Utils/ToolUtils.cs#L501) 的 `RetryOnFileBusy(() => new Track(...))` 改为裸 `try { track = new Track(file.Path); } catch`（主路径 GetMusicInfo 已耗尽 ~12s 重试，这里只做廉价补读；同时让被占用文件最多占用信号量槽 ~12s 而非 ~24s）。
- **ffmpeg 补齐**：在现有属性系统字段合并完成、`return fileInfo` 之前（约 :526）插入：

```csharp
if (fileInfo.Duration <= TimeSpan.Zero || fileInfo.SampleRate == 0 ||
    fileInfo.ChannelCount == 0 || fileInfo.BitRate == 0)
{
    try
    {
        if (FFmpegMetadataProbe.TryProbe(file.Path, out var p))
        {
            // 仅补缺失字段，已有非零值不覆盖；DSD 位深特判（=1）保持优先
            if (fileInfo.Duration <= TimeSpan.Zero && p.DurationMs > 0) fileInfo.Duration = TimeSpan.FromMilliseconds(p.DurationMs);
            if (fileInfo.SampleRate == 0) fileInfo.SampleRate = p.SampleRate;
            if (fileInfo.ChannelCount == 0) fileInfo.ChannelCount = p.Channels;
            if (fileInfo.BitRate == 0) fileInfo.BitRate = p.BitRateKbps;
            if (bitDepth == 0 && !IsDsdExtension(file.Path) && p.BitDepth > 0) fileInfo.BitDepth = p.BitDepth;
        }
    }
    catch (Exception ex) { _logger.LogWarning(ex, $"FFmpegProbe 兜底失败: {file.Path}"); }
}
```

DSD 的 `BitDepth=1` 特判（:510）维持现状不动。健康文件路径零额外开销。

### 3. `Services/AddFolderService.cs` — 批次化扫描（重写 GetMusicFilesRecursive，~60 行）

新签名（替换旧方法，旧方法删除）：

```csharp
public async Task GetMusicFilesRecursiveBatched(StorageFolder folder,
    Func<IReadOnlyList<(Music Music, string Lyrics)>, Task> onBatch)
```

- 每目录：`GetFilesAsync` 过滤 `IsMusicFile` → 并行 `GetMusicInfo`（沿用静态信号量 8）→ 按目录顺序入本地缓冲，缓冲满 `ScanBatchSize`(100) 即 `await onBatch(buffer)` 并重置缓冲；目录尾批冲一次；随后并行递归子目录（与现状相同的 `Task.WhenAll` 递归）。
- 单文件异常仍按现状记日志跳过（GetMusicInfo 返回 null 项不入批）。
- 删除死代码依赖方 `GetMusicListByFolder`（MusicDatabaseService.cs:1383）。

### 4. `Services/MusicDatabaseService.cs` — 批次入库回调（~40 行）

```csharp
public async Task CheckFolderBeforeAdd(StorageFolder folder,
    Func<Folder, Task>? onFolderInserted = null,
    Func<IReadOnlyList<Music>, Task>? onBatchInserted = null)
```

- 重叠检查/子文件夹清理逻辑不动；`InsertAsync(newFolder)` 之后、扫描之前：`if (onFolderInserted != null) await onFolderInserted(newFolder);`（Folder.Id 已回填）。
- `ScanFolderAsync` 加可选参数 `Func<IReadOnlyList<Music>, Task>? onBatchInserted = null`：

- `RescanFolderByPath` / `RescanFolderWithOutUpdateAll` / AutoRescanService 相关签名全部不动。

### 5. `ViewModel/AppViewModel.cs` — 增量应用入口（+25 行）

```csharp
/// <summary>扫描批次渐进应用（仅 UI 线程调用）：追加 SongsSource 与 id 索引，
/// 翻转空库占位，只刷新当前页；分组/排序索引由收尾全量刷新修正。</summary>
public void AppendSongsBatch(IReadOnlyList<Music> batch)
{
    if (batch.Count == 0) return;
    SongsSource.AddRange(batch);
    for (int i = 0; i < batch.Count; i++) _idIndex[batch[i].Id] = batch[i];   // 新 Id 无冲突，无需置 _indexDirty
    if (LibraryEmptyVisibility == Visibility.Visible && SongsSource.Count > 0)
        LibraryEmptyVisibility = Visibility.Collapsed;
    if (IsInitialized) RefreshDataForPageType(AppData.CurrentPage);
}
```

不调用 `NotifySongsSourceChanged`。`RefreshSongsSourceAsync` / 收尾路径零改动。

### 6. `ViewModel/Pages/AddFolderViewModel.cs` — 状态机与合并器（~80 行）

- 新增 `public bool IsScanning`（`[NotifyCanExecuteChangedFor(nameof(AddFolderCommand))]`），`AddFolderAsync` 的 `[RelayCommand]` 挂 `CanExecute = nameof(NotScanning)`（AddFolderPage 两处按钮与空库占位按钮都绑定该命令，CanExecute 自动禁用，无需改 XAML）。
- 批次合并器（核心新逻辑）：

```csharp
private const int UiFlushIntervalMs = 500;
private readonly object _pendingLock = new();
private List<Music> _pendingUiBatch = [];
private DispatcherQueueTimer? _uiFlushTimer;   // UI 线程创建，单次触发
private Folder? _activeScanFolder;             // 当前扫描文件夹，用于 SongCount 实时累加

private void EnqueueUiBatch(IReadOnlyList<Music> batch)   // 扫描线程回调
{
    if (batch.Count == 0) return;
    lock (_pendingLock) _pendingUiBatch.AddRange(batch);
    App.MainWindow?.DispatcherQueue.TryEnqueue(EnsureFlushTimer);   // 幂等
}

private void EnsureFlushTimer()                            // UI 线程
{
    _uiFlushTimer ??= App.MainWindow.DispatcherQueue.CreateTimer();
    // 初始化：IsRepeating=false, Interval=500ms, Tick += FlushPendingUiBatches
    if (!_uiFlushTimer.IsRunning) _uiFlushTimer.Start();
}

private void FlushPendingUiBatches()                       // UI 线程，≤2Hz
{
    List<Music> toApply;
    lock (_pendingLock) { toApply = _pendingUiBatch; _pendingUiBatch = []; }
    if (toApply.Count == 0) return;
    AppViewModel.AppendSongsBatch(toApply);
    if (_activeScanFolder is not null) _activeScanFolder.SongCount += toApply.Count;
}
```

- `AddFolderMusic(folder)` 重写：

```csharp
private async Task AddFolderMusic(StorageFolder folder)
{
    if (folder is null || IsScanning) return;
    IsScanning = true;
    try
    {
        await Task.Run(() => _musicDatabaseService.CheckFolderBeforeAdd(folder,
            onFolderInserted: f =>
            {
                _activeScanFolder = f;
                // UI 线程：新文件夹行先出现（空态→列表态在此翻转）
                App.MainWindow.DispatcherQueue.TryEnqueue(() => { if (!FolderList.Contains(f)) { FolderList.Add(f); SetVisualStateOnUi(false); } });
                return Task.CompletedTask;
            },
            onBatchInserted: batch => { EnqueueUiBatch(batch); return Task.CompletedTask; }));
        // 收尾：冲净残留批次 + 一次全量刷新修正排序/分组/歌单映射 + 文件夹计数复核
        App.MainWindow.DispatcherQueue.TryEnqueue(FlushPendingUiBatches);
        await AppViewModel.RefreshSongsSourceAsync();
        await LoadFoldersAsync();
    }
    finally
    {
        _activeScanFolder = null;
        IsScanning = false;
        SetVisualStateOnUi(false);
    }
}
```

- `AddFolderWithLoadingAsync`：picker 返回 null 直接 return（不置 IsScanning、不动视觉态）；有结果才进 `AddFolderMusic`；**不再** `SetVisualStateOnUi(isLoading:true)`（Loading 遮罩仅保留给重扫/移除）。
- `DropFoldersAsync`：去掉 Loading 遮罩，顺序 `await AddFolderMusic(...)` 各文件夹（首个文件夹的 onFolderInserted 使列表态出现），异常记日志。
- `RescanFolderWithLoadingAsync` / `RemoveFolderWithLoadingAsync`：开头加 `if (IsScanning) return;`，其余不动（Loading 遮罩保留且天然防重入）。

## 不做的事（明确边界）

- `RescanFolderByPath` / 自动重扫（AutoRescanService）不批次化——保持签名与行为稳定，留作后续。
- `SaveEmbeddedLyricsAsync` 不改批量实现（逐行但量小）。
- 不引入 CancellationToken 贯穿扫描（现状也没有；IsScanning 防重入已足够）。
- ffmpeg 不参与标题/歌手/专辑/歌词解析，不在健康文件路径运行。

## 边界与风险

- **排序正确性**：渐进期当前页按现有排序全量重建（`RefreshDataForPageType` 内含排序+FillFrom(Reset)），批内顺序本就按目录产出；收尾全量刷新保证最终一致。
- **ListView Reset 成本**：`RefreshDataForPageType` 每次冲刷是 Reset 语义（BulkObservableCollection 所有批量操作均 Reset，无 Add 通知）。500ms 节流 + ListView 虚拟化下可接受；若超大库（>2 万首）实测仍有抖动，后备优化是 SongListPage+DefaultOrder 时改 `ListSongs.AddRange` 直追（同为 Reset，省排序），本次不实现。
- **PlayListSongs / SequentialPlayingList**：渐进期不重建歌单映射（ID 映射，追加 SongsSource 不破坏现有引用）；收尾刷新统一修正——与今日行为一致。
- **sqlite 并发**：批次 `InsertAllAsync` 与自动重扫的写并发性与现状相同（SQLiteAsyncConnection 串行化），不引入新风险。
- **扫描中退出应用**：已入库批次为完整有效行，下次启动正常加载（与今日中断行为一致）。

## 实施顺序

1. `FFmpegMetadataProbe.cs` + `GetAudioInfo` 改造（独立，先落地可单独验证损坏文件场景）；
2. `AddFolderService` 批次化 + `MusicDatabaseService` 回调（含死代码删除）；
3. `AppViewModel.AppendSongsBatch` + `AddFolderViewModel` 状态机/合并器 + `FolderCommands` 防重入；
4. `MusicBrowseViewModel` 空库入口解耦；
5. 构建验证 + 手动场景回归。

## 验证方案

- `dotnet build` 通过。
- 手动场景（需运行应用）：
  1. 空库拖入含数百首的文件夹：占位在首批（~1s 内）消失，歌曲列表渐进增长，无 ProgressRing；
  2. AddFolderPage 添加新文件夹：文件夹行先出现，SongCount ~500ms 步进递增，结束值与最终一致；
  3. 扫描中再点"添加文件夹 / 重新扫描 / 移除"：被 IsScanning 拦截；
  4. 扫描完成后切换 A-Z/歌手/专辑/文件夹视图与歌单：排序与分组正确（收尾全量刷新生效）；
  5. USB 传输与文件监视自动重扫：顶部进度环行为不变；
  6. 混入损坏文件/改后缀文件：日志可见 ATL→属性系统→ffmpeg 链路，最终条目不缺时长/采样率；被外部程序占用的文件重试总时长减半（~12s 封顶）。
